# `scripts/lens/` — library-component profiling

Every other script tree in this repo is laid out **dataset-first**
(`scripts/<dataset>/<task>/<model>.py`): pick a dataset family, pick a task, get
the cost of a *pipeline*. That axis answers *"how long does this fit take?"*.

`scripts/lens/` is the second axis, and it is deliberately **dataset-free**. Its
cells profile a single **library component** — one function, on one grid, with
one set of fiducial parameters — and answer a different question:

> *"How much does this one piece of the lensing calculation cost per call, and
> where inside it does the time go?"*

A dataset is still loaded, but only to build a realistic grid; nothing about the
data enters the measurement. Swapping the instrument changes the number of grid
points and nothing else, which is exactly the knob these cells want.

## Why a second axis

A pipeline breakdown tells you *which step* dominates. It cannot tell you what
that step would cost if you called it differently, on a bigger grid, or with a
different profile in the model — because the step is welded to the pipeline that
contains it. When the optimisation target is a library primitive rather than a
pipeline (the `numpy-deflections-cpu` epic is the first such case), the
before/after evidence has to be measured on the primitive itself, or the
pipeline's own variability swamps the change you made.

These cells are therefore the *before* and *after* record for library-level
performance work: cheap to run, stable across releases, and pinned on the
**numbers** the component computes so a speed-up that quietly changed an answer
cannot pass as a win.

## Sections

| Section | Component | Question |
|---------|-----------|----------|
| [`deflections/`](./deflections/README.md) | `MassProfile.deflections_yx_2d_from` | What does one deflection-angle evaluation cost, per mass profile, on the numpy CPU path? |

Planned siblings follow the same shape, one component per folder:
`convergence/`, `potential/`, `shear/`.

## Conventions

Identical to the rest of the repo — the axis changes, the mechanics do not:

- Run from the repo root: `python scripts/lens/<section>/<cell>.py`.
- Each cell writes a versioned artifact pair under
  `results/lens/<section>/<cell>_summary_<instrument>_v<version>.{json,png}`.
- `AUTOLENS_PROFILING_SMOKE=1` short-circuits after the imports (the CI lint
  gate runs one cell per section this way).
- The auto-tables in each section README are regenerated by
  `python scripts/misc/tooling/build_readme.py` and gated by its `--check` mode.

Unlike the dataset-first tasks, these sections keep their shared driver **beside
the cells** rather than under `scripts/misc/<task>/`: the driver is the section's
methodology, not a cross-dataset framework, and the cells are meaningless without
it.
